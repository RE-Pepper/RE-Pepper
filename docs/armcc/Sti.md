# __sti and .init_array

how static initializers work in the game, and what the build
does with them.

## what armcc generates

a TU with a static that has a constructor gets one generated init
function, named after the file:

```
__sti___<len>_<stem>_cpp      example: __sti___10_Togezo_cpp
```

the name is a length prefixed mangle of the TU stem, so
`tools/low/readElfSym.py` must match the file symbol exactly and not
by substring, or every __sti gets filtered out of `.syms` and can
never pin.

## the table that calls them

the original wires the __stis through a `.init_array` table, the C
library walker calls each entry at startup:

```
__cpp_initialize__aeabi_   the walker (stock libc fn)
.init_array table          right after the walker, ends exactly
                           at text end, 4 bytes per __sti
```

entry encoding, verified against the libc implementation
(`armlib/c_2.b:init_aeabi.o`) and our own build:

```
target = entry + its own slot address
```

each entry is negative (targets sit below the table), so every
word starts with 0xff. the walker does `add r0, r0, r4` where r4
is the current slot pointer, then calls it. position independent
by construction.

the empty table edge case is real and handled: the stock libc
default points base and limit at the same address and the loop
checks the bounds before the first call. the
`__cpp_initialize_dummy_init_array` weak fallback exists for
links with no init at all.

the walker exists in two variants: ARM-only (`mov pc, r0`) and
interworking (`blx r0`). which one links depends on the build's
`--apcs` setting. `--arm_only` selects the ARM variant.

## entry order is not a sort

nobody sorts the table. the order is the linker's archive scan:
each run is one scan pass over one archive in its internal
(alphabetical) member order, and the runs stack in the order the
linker pulled them. pass 1 is what the crt chain references
directly, the last entry is the deepest resolved TU.

consequence: the table is a fingerprint of the whole link
resolution. it can only match when object order, archive
contents and the reference graph all match. it will be the last
thing that matches.

## matching support

- `.syms` sees __stis (readElfSym fix above)
- map rows for all __stis plus the `.init_array` data row and
  the walker
- two row conventions exist:
  - hand rows (136) use IDA's function end, pool excluded. a
    compiled __sti section includes its pool, so those pins
    can't fit and demote. fine for now: demote is the safe
    default.
  - generated rows (481) use the next symbol start, full span
    including pool. pins can fit.
- a modified __sti that doesn't match demotes to `.matchskip`
  like any other bad pin. to retry after fixing the source,
  remove it from `.matchskip` again. changes to already demoted
  __stis are not re-attempted automatically.
- our own `.init_array` is generated by armlink whenever a TU
  gains a constructor static (4 bytes per __sti, slot relative,
  same encoding). it lands in the spill today, the row exists so
  the day the full __sti set matches the table can pin at the
  table address.

## workflow

```
1. pick a row from data/ver/eu/.demote_backlog.txt (or any __sti)
2. remove it from .matchskip
3. python3 make.py eu --match
4. tools/diff.py            -> exact differing bytes, or MATCH
5. fix the statics in the TU, repeat
6. tools/diff.py --update   -> demote what still differs, stay MATCH
```

## edge case: constant folding

a trivial constructor (constant stores, no external calls) may
be folded at compile time. the static then has no __sti and no
.init_array entry at all, the values bake into .data directly.
verified with a test TU: armcc at -O3 with VFE kept the __sti,
but the encoder could fold it in other cases. if a TU you expect
to have an __sti doesn't, check for folding first.

## edge case: length prefix

the length in `__sti___<len>_<stem>_cpp` counts the stem plus
"_cpp", e.g. StiTest.cpp -> `__sti___11_StiTest_cpp` (11 chars
"StiTest_cpp"). don't guess it from the stem alone.
