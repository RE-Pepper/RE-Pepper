# armcc runtime initialization

how the C library starts up, initializes statics and calls main.
the mechanism is verified from binaries and the armlib
implementation shipped in `data/compilers/4.0/902/lib/armlib/`.

## the chain

```
__ctr_start -> _mainCRTStartup -> __rt_entry
             -> __rt_stackinit, __rt_lib_init (heap, libc)
             -> __cpp_initialize__aeabi_     (calls .init_array)
             -> __rt_lib_shutdown ...
             -> main / nnMain
```

## __cpp_initialize__aeabi_

the stock C library function that calls all static initializers.
implementation in `armlib/c_2.b:init_aeabi.o`:

```
push {r4, r5, r6, lr}
r4 = table base  (pc-relative)
r5 = table limit (pc-relative)
loop:
    r0 = [r4]
    r0 = r0 + r4        ; entry + slot address
    call r0
    r4 += 4
    if r4 != r5 goto loop
pop
```

the default build (no .init_array section) has both literals
pointing at the same address, so the loop runs zero times.

## .init_array

- generated by armlink, one 4-byte entry per `__sti` function
- entry encoding: `target = entry + its own slot address`
  (self-relative, position independent)
- all entries are negative (targets sit below the table), so
  every word has the top byte 0xFF
- the walker's `add r0, r4` makes this work: r4 is the current
  slot pointer, not a fixed base

in a binary:
```
walker: __cpp_initialize__aeabi_  right before the table
table:  N entries, ends exactly at text end
```

the number of entries equals the number of TUs that have static
initializers. adding a static with a constructor to a TU that
had none grows the table by 4 bytes.

## entry order

nobody sorts the table. the order is armlink's archive scan order:
each alphabetical run is one scan pass over one archive in its
internal member order. the runs stack in the order the linker
pulled them (dependency resolution order).

this means the table is a fingerprint of the entire link. it
can only match when object order, archive contents and the
reference graph all match simultaneously.

## arm-only vs interworking

the walker exists in two variants: ARM-only (uses `mov pc, r0`
after setting up lr) and interworking (uses `blx r0`). the
armlib ships both, which one gets linked depends on the build's
`--apcs` setting. redpepper builds with `--arm_only` so the
ARM-only variant is what ends up in the binary.

## nninitRegion

separate from .init_array: the nnSDK's startup zeroes the BSS
region between two linker-provided addresses. it reads:

```
__ctr_start zeroes [start, end) word by word
```

the addresses are in the literal pool, they correspond to the
BSS span from the ELF header.

## STATIC_INIT

the nnSDK also references `Image$$STATIC_INIT$$RO$$Base/Limit`
from `init_StartUp.cpp`. in a binary where the nnSDK used a
different init path than the compiler's .init_array, both point
to the RO end and the range is empty. the nnSDK collects
pointers via a static table that the linker fills, but that
table can have zero entries.

the two mechanisms are independent. a build can have .init_array
entries and an empty STATIC_INIT, or the reverse.
